# 服务注册与配置中心方案报告

> 主题：服务间地址硬编码的收敛方案（rag→embedding/reranker、infer→upstream 等）
> 结论先行：**API 网关平台已具备服务注册中心与服务发现 API，配置中心服务端已具备但客户端拉取通道缺失**；本地开发调试可以接入（已实测跑通）。建议按"三步走"收敛，并向网关平台团队提出 2 项增量需求。

## 一、问题盘点（地址硬编码现状）

| 类别 | 位置 | 现状 |
|------|------|------|
| py 服务间直调 | py-genai-rag → embedding(38103)/reranker(38104) | `EMBEDDING_URL`/`RERANKER_URL` 环境变量可覆盖，默认 localhost |
| py 网关上报 | 9 个 py 模块 `gateway_report_url` | 原硬编码 `localhost:9000/api/report`（错误端点），本次已收敛为 `GATEWAY_SERVER_ADDR`（默认 `http://127.0.0.1:28090/api`） |
| py 死配置 | infer `upstream_url`/`INFER_UPSTREAM_KEY` | 转发收敛到 router 后已无调用方（遗留，可清理） |
| Java 直调 | jv-genai-comm → auth(38081)；auth/user → 网关(9000/28081) | `@Value` 默认 localhost，可被 yml 覆盖 |

## 二、API 网关平台能力检查结论（project_api-gateway）

### ✅ 已具备（无需对方开发）

| 能力 | 接口 | 说明 |
|------|------|------|
| **服务注册中心** | `POST /discovery/services/register`、`/heartbeat`、`DELETE /deregister` | 按 serviceId 幂等 upsert，payload：appId/serviceId/ip/hostname/port/language/version |
| **服务发现 API** | `GET /discovery/services`（keyword/serviceId/status/language 过滤分页） | "服务名 → ip:port"查询能力存在 |
| **主机指标采集** | `POST /discovery/metrics/batch`（60s 周期） | cpu/mem/disk/net/gpu 全套，入库 tb_gw_host_metrics |
| **调用日志采集** | `POST /trace/logs/batch`、`/trace/spans/batch` | 内存队列异步批量，入库 tb_gw_trace_log / tb_gw_trace_span |
| **配置中心（服务端）** | `GET/POST/PUT/DELETE /configs`（存储可落 DB/Redis/Nacos）+ 动态日志级别 `/policies/log-levels` | 平台服务 10s 内生效 |
| **统一入口** | `http://127.0.0.1:28090/api`（proxy 按 tb_gw_route 转发） | 客户端鉴权 `X-Gateway-Client-Token: dev-gateway-token` |

### ⚠️ 缺口（需对方评估/开发，见第五节清单）

1. **客户端 SDK 无配置拉取通道**：`jv-api-gateway-client-starter` 只有注册/心跳/下线/上报/验签 5 类端点，**没有**配置轮询/长连接监听——配置中心目前只对网关平台自身服务生效，接入方消费不到
2. **无客户端服务发现组件**：发现只有"查询 API"，没有带本地缓存、故障转移、负载均衡的客户端 SDK（调用方需自己轮询 + 选实例）
3. 查询类接口走平台登录鉴权（client-token 只覆盖注册/上报类），服务间程序化查询需确认放开策略

### ✅ 本地开发调试接入：可以，且已实测跑通

- Java 侧早已接入（`jv-genai-apigateway-client-sdk` 壳模块 → jv-api-gateway-client-starter，scheduler 等服务启动即自动注册上报）
- **本次 Python 侧已完成接入**（py-genai-apigateway-client-sdk v0.2.0，9 个 py 模块全部接线）：infer 实测注册 → 心跳 → 状态"健康" → 请求采集落库 → 优雅下线"离线"，全程无报错
- 本机调试零门槛：网关平台 28090 在跑 + 默认 token 即可；换环境只需 `GATEWAY_SERVER_ADDR` / `GATEWAY_CLIENT_TOKEN` 两个环境变量

## 三、方案设计（三步走）

### 第一步（已完成）：SDK 接入 + 采集 + 上报地址收敛

- Python SDK 升级为完整版（对齐 Java SDK 能力）：注册/心跳/下线、主机指标（psutil）、调用日志批量上报、FastAPI 一行接入中间件、`discover()` 服务发现查询
- 9 个 py 模块 `gateway_report.py` 重写为 SDK 适配层（init=注册+心跳+指标+采集；install=请求采集中间件；stop=优雅下线），`gateway_report_url` 硬编码清除，改 `GATEWAY_SERVER_ADDR` 环境变量
- 效果：py 服务与 Java 服务在网关平台同一视图可见（注册状态/主机指标/调用日志），排查不再需要逐个看日志

### 第二步（建议 1 周内）：服务间调用收敛到 router 统一路由

- **rag → embedding/reranker 改走 router**：rag 服务的 `embedding_url/reranker_url` 改为指向 router(38100)，`model` 填平台名（studio-embedding/studio-reranker）——复用 router 的鉴权/限流/计费/双日志，服务间调用也有完整审计；地址只配 router 一个
- **清理 infer 死配置**：删除 `upstream_url`/`upstream_api_key`
- **Java 直调保留**（auth 校验链属框架级依赖，收益低），仅把 jv-genai-comm 的默认值抽到平台配置

### 第三步（依赖网关团队，见第五节）：配置中心客户端 + 发现客户端组件

- 配置项（如 `EMBEDDING_URL`、单价表、日志级别）从"进程内默认值"迁移为"网关配置中心下发 + 本地缓存兜底"
- 服务发现从"静态配置"升级为"启动时发现 + 定期刷新 + 实例健康过滤"

## 四、过渡期兼容设计（已内置）

- 所有新配置均有环境变量出口 + 合理默认值（`GATEWAY_SERVER_ADDR` 等），网关平台不在时 py 服务照常启动（注册失败仅 warning，心跳自动补注册）
- rag 的 `EMBEDDING_URL/RERANKER_URL` 环境变量语义保持不变，第二步收敛时默认值改为 router 地址即可，代码零改动

## 五、需网关平台团队开发的需求清单

| # | 需求 | 说明 | 优先级 |
