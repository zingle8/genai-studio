# 推理服务 — 模块说明

- 服务 ID：`py-genai-infer`
- 端口：38101
- 代码来源：本地 MLX 模型的加载与推理执行器（mlx_lm 纯文本 / mlx_vlm 多模态）；统一转发收敛到 jv-genai-router
- 状态：**已跑通完整链路**（2026-11-24）：`调用方 → jv-genai-router(38100) → 本服务(38101) → MLX Metal GPU`，含 usage 计费落库
- 模型：`mlx-*` 别名（与 `tb_model_info.real_name` 对应）经 `app/model_registry.py` 映射到 `local_models/mlx-community/<目录>`；按 real_name 懒加载并缓存引擎（4 个模型不同时驻留内存）

## 并发与性能设计（2026-11-25 实测通过）

- **线程亲和**：MLX GPU stream 是线程局部的（`There is no Stream(gpu, N) in current thread`），每个模型绑定一个专用单线程 `ThreadPoolExecutor`，加载/推理都在同一线程；不同模型可并行
- **非阻塞**：async 路由通过 `run_in_executor` 调用同步 MLX 调用，事件循环不阻塞
- **加载去重**：同模型并发首次请求只加载一次（Event 等待），统计 `dedup_waits`
- **LRU 淘汰**：`INFER_MAX_LOADED_MODELS`（默认 4，128GB 内存可全驻留 4 模型）限制驻留模型数，超出释放内存，统计 `evictions`
- **并发限流**：`INFER_MAX_CONCURRENCY`（默认 2）每模型信号量；`INFER_WORKER_THREADS`（默认 4）兼容配置
- **全局推理闸门**（2026-11-25 新增）：`INFER_MAX_GLOBAL_INFLIGHT`（默认 2）跨模型 BoundedSemaphore，非流式 `_generate_sync` 与流式 `produce()` 统一在真正进入 MLX 推理前 acquire、结束 release；流式整个产出周期持锁。这是防 GPU hang 的关键——即使 3+ 模型同时收到请求，同时进入 Metal GPU 推理的也 ≤ 2，其余排队。统计 `global_gate_waits`/`global_inflight_now`/`global_inflight_peak`
- **SSE 流式**：`stream=true` 逐 token 输出，末帧带精确 usage（来自 `GenerationResponse`），经 asyncio.Queue 桥接
- **可观测**：`GET /v1/stats` 查看 loads/evictions/load_errors/dedup_waits/驻留数/全局闸门状态
- **网关侧**：体验中心-本地免费 Key 限流 `rpm=360 / cc=8`（`genai_apikey.tb_api_key`），与服务端闸门形成双层保护；cc=8 匹配双实例最优并发点
- **单模型多实例**（2026-11-25 启用）：`mlx-glm-4.7-flash` 双实例（38101 + 38102，各 `INFER_MAX_GLOBAL_INFLIGHT`=1），`tb_model_info.base_url` 逗号分隔多地址，`RelayController.pickBaseUrl()` 用 `AtomicInteger` 原子轮询分发（单地址向后兼容）。实例 2 用 `run-instance2.sh` 启动。其余 3 个模型仍单实例 38101
- **压测结果**（2026-11-25）：
  - 单模型梯度 1→32 并发：全部 100% 成功，RPS 峰值 2.4（并发 2 时），并发 32 时 P99 6.78s；事件循环不阻塞（/health < 0.3s）
  - 多模型真并行：4 模型全驻留（resident=4，evictions=0）；3 模型各 1 请求总耗时 2.21s（≈ 最慢单请求，非串行之和）
  - 优化前后对比：多模型混合 9 请求从 8.67s/1.04 RPS → 6.26s/1.44 RPS（消除 LRU 重载后提速 38%）
  - SSE 经 router 透传正常，计费 token 正常（17+6 落库）
  - 持续 20s 压测吞吐：单模型 2.4 RPS、双模型各×4 共 3.15 RPS、双模型各×8 共 3.55 RPS（均 100% 成功）
  - **GPU 极限**：3 模型同时持续推理曾出现 Metal GPU Hang（kIOGPUCommandBufferCallbackErrorHang），3 模型各×2 起约 3-10% 500 错误；安全上限 = 2 模型同时推理。4 模型可全驻留（resident=4）但不要同时打满
  - **全局闸门回归压测（2026-11-25，闸门后）**：3 模型各×1/×2/×4 持续 20s 全部 100% 成功、零 500、零 GPU Hang（闸门前 ×2 起就报错）；`global_inflight_peak=2`、`global_gate_waits=50`（多余并发被排队）；双模型各×8 共 3.60 RPS。代价是 3 模型各×4 时 P95 升到 28.3s（排队等待），属预期的稳定性换吞吐取舍
  - 单模型瞬时并发 8 全部成功（P95 3.4s），但吞吐不随并发线性增长（RPS 稳定 2.4）
  - **双实例轮询压测（2026-11-25，GLM）**：直连双实例各×8 达 4.70 RPS；经 router 端到端并发 8 = 4.27 RPS、零错误（P95 2.32s），较单实例 2.4 提升约 78%；两实例同模型并发无 GPU hang（38101 peak=2、38102 peak=1）。并发 ≥12 的 429 来自网关 CC=8 限流（设计内保护，非 GPU 问题）
