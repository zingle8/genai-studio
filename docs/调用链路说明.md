# GenAI Studio — 调用链路说明

> 各模块间请求与转发流程（截至 2026-11-13，已实现状态）。
> 核心原则：**jv-genai-router 是唯一转发收口**——所有模型推理（外部云端 / 本地执行器 / Ollama）都经 router，鉴权 / 限流 / 计费 / 日志只在 router 做一次。

## 一、总览拓扑

```
浏览器（fe-chats 体验中心 38202 / fe-admin 管理面 / 外部 SDK）
    │
    ├──────────────────────────┐
    ↓ (推理：带 API Key)         ↓ (存储：平台登录态)
jv-genai-router 38100 ←──── jv-genai-chats 38090
[鉴权→限流→余额→转发→计费/日志]     [会话/消息 CRUD 落库]
    │ 按 tb_model_info 每请求实时查库，动态转发
    ├→ 外部云端厂商 API（GLM / DeepSeek / Claude / Gemini…）
    ├→ Ollama 11434（文本/多模态/OCR/向量 12 个本地模型）
    ├→ py-genai-infer 38101        （studio-chat，本地 HF 生成推理）
    ├→ py-genai-rag-embedding 38103（studio-embedding，向量化）
    ├→ py-genai-rag-reranker 38104 （studio-reranker，重排）
    └→ py-genai-rag-systemone 38109（studio-laya / studio-nanojev，判断）
```

## 二、四条链路（按模型类型）

### 1. 外部 chat / 多模态模型

```
调用方 → router(38100) → 云端厂商 API
```

### 2. 内部 chat / 多模态模型

```
调用方 → router(38100) → 两条并列分支（不互相经过）：
   ├→ studio-chat  → infer(38101)：本地 HF 模型加载 + generate 推理
   └→ Ollama 模型  → 11434：Ollama 自身完成推理（等同"本地版厂商"）
```

### 3. 外部向量 / 重排 / 判断模型

```
调用方 → router(38100) → 云端厂商 API
例：GLM-Embedding-3 → 智谱 /v1/embeddings
```

### 4. 内部向量 / 重排 / 判断模型

```
调用方 → router(38100) → 四个并列内部执行器：
   ├→ rag-embedding(38103)   studio-embedding                向量化
   ├→ rag-reranker(38104)    studio-reranker                 重排
   ├→ rag-systemone(38109)   studio-laya / studio-nanojev    判断（choice/score/boolean）
   └→ Ollama(11434)          qwen3-embedding / nomic-embed   向量化
```

## 三、chat 类与向量/重排/判断类的差异

| 维度 | chat / 多模态 | 向量 / 重排 / 判断 |
|------|--------------|-------------------|
| 接口路径 | `/v1/chat/completions` | `/v1/embeddings`、`/v1/rerank`、`/v1/laya/decide`、`/v1/nanojev/decide` |
| 请求体 | `messages` 数组 | embeddings=`input` 数组；rerank=`query+documents`；systemone=各题型自有格式 |
| 响应结构 | `choices[0].message` | 向量数组 / 排序分数 / 判断结果 |

router 对所有类型同一套处理：每请求查 `tb_model_info`，按该模型登记的 `url_paths` 白名单匹配路径（未开放 → 400），`model` 替换 `real_name`，透传响应，按 tier 单价 × usage tokens 计费，写日志。调用方唯一规则：**带 API Key 请求 router，body 的 `model` 填平台名**。

## 四、router 内部校验链（每次转发）

```
转发前：
  1. 鉴权：Authorization Bearer → genai_apikey.tb_api_key（有效/未过期/模型白名单）→ 401/403
  2. 限流：RPM/TPM 固定分钟窗口（Redis+MySQL 双写，Redis 故障熔断降级 MySQL）+ CC 并发信号量 → 429
  3. 余额：genai_billing.tb_account_balance ≤ 0 → 402
转发后：
  4. 计费：tier 单价（tb_model_price：旗舰/标准/免费）× prompt/completion tokens → 扣余额
  5. 日志：tb_usage_log（计费统计）+ tb_relay_log（请求/回复原文，64KB 截断）
     两表 trace_id 同源精准对齐，JOIN 可还原"一次调用的费用+内容"
```

## 五、体验中心一次对话全流程

```
1. 用户输入 → fe-chats(38202) vite 代理
2. POST router:38100/v1/chat/completions（Bearer API Key）
3. router 校验链（第四节）→ 转发对应执行器 → 推理 → 透传响应 → 计费/日志
4. fe-chats 收到回复 → POST chats:38090/{id}/messages/batch 批量落库
   （tb_chat_message 按日分区；trace_id 区分轮次：1 条 user + N 个模型回复）
5. 历史还原：GET chats:38090/{id}/messages（气泡按 model 标注多模型回复）
```

**chats 与 infer 互不调用**：chats 是会话存储（Java/MySQL），infer 是推理执行器（Python），由前端分别连接，职责分离。

## 六、RAG 流水线（模块协作形态，知识库上线后）

rag 三模块是检索增强流水线的工序，router 使其可独立调用；串接编排服务（知识库）建设中：

```
① embedding(38103)：问题 → 向量
② 向量库检索 → 候选 top-k（编排服务建设中）
③ reranker(38104)：query + documents → 精排
④ systemone(38109)：结果判断（choice/score/boolean）
⑤ 拼装上下文 → chat 模型生成最终回答
```

## 七、模块职责一句话

| 模块 | 端口 | 职责 |
|------|------|------|
| jv-genai-router | 38100 | 唯一收口：转发 + 鉴权/限流/计费/内容日志 |
| jv-genai-chats | 38090 | 体验中心会话存储（不管推理） |
| py-genai-infer | 38101 | 本地 HF 生成模型推理（不转发） |
| py-genai-rag-embedding | 38103 | 向量化（dense/sparse/colbert/hybrid） |
| py-genai-rag-reranker | 38104 | 检索精排 |
| py-genai-rag-systemone | 38109 | 判断题执行器（choice/score/boolean 三题型 ×2 模型） |
| Ollama | 11434 | 本地模型运行时（文本/多模态/OCR/向量 12 个） |
